What does a product design engineer actually do?

The same thing a product designer does, carried one step further: into the codebase, where the component is the deliverable and the design system is a folder of files everyone can read. The day is made of components, tokens, branches, pull requests and checks, and the design judgment does not move; it gets attached to evidence. The worked example is Agent Review, a React and Storybook system I built to see where that judgment goes when a coding agent writes the interface.

Key idea 1 of 8

The handoff did not move; it dissolved

For years the shape of a design job was a document that went somewhere else. You made the file, somebody built from the file, and the distance between the two was where the quality leaked out. AI coding tools moved that line: a designer can now build the thing, verify it and stand behind it. I came to this side of it from product design, enterprise design systems and UX architecture, not from engineering. React, TypeScript and Storybook are tools I now use to carry that work into code, and the evidence here is one project built that way, Agent Review, and the site you are reading.

The short version: there is no far side. A design engineer is a designer whose deliverable is the thing itself, in the repository, next to everyone else’s. The judgment is the same judgment. What changes is that every decision now has evidence attached, because it is code that runs, and a colleague can open it.

Key idea 2 of 8

The component is the deliverable, and it lives in one place

In a product codebase the unit of design is a component: a button, a data table, a status line, a card. In React it is a function that takes properties and returns markup, and in TypeScript the properties are typed, which means the contract between design and engineering is a list the compiler reads rather than a note in a Figma frame. Agent Review has thirteen components, and the Button is the plainest of them: primary, secondary, danger or ghost, default or compact, loading, disabled. That is one file, and ten stories show its states.

The showroom for that file is Storybook: every component, every state of it, rendered on a page a designer can open without running the product. It is the design system’s own site, generated from the system, and it is the single artifact a design engineer most clearly owns. If the story for a component is wrong, the component is wrong. Agent Review has 161 of them, and every story is also a test: Vitest renders it in Chromium and runs axe on it, with violations set to fail. A state with no story is a state nothing checks.

This site is the same idea at a smaller scale: three token files and a component set in plain HTML and CSS, with Node scripts standing where a build would. Agent Review is the same idea in the vocabulary a product team would recognize, and I built it to answer a design question rather than to ship a product. It has one author, one scenario and no users, so what I can say about it is what it taught me about the work, not that I have run a production React codebase. I would rather say that here than have it discovered.

Key idea 3 of 8

Tokens flow one way, from a file everyone can read

A design system that lives in code has one source for every value: a file of tokens, usually JSON, that says what --color-accent is and what --space-lg is. A tool such as Style Dictionary turns that file into whatever each platform needs: CSS custom properties for the web, constants for iOS and Android, a table for the documentation. Tokens Studio does the same from inside Figma. The direction is what matters. The file is upstream of everything, so parity between the design and the code is not a review step; it is the only way the values exist.

The vocabulary the design-engineer postings use comes straight from this file. A primitive token is a raw value with a plain name: a green, a size. A semantic token says what the value is for: the accent, the text on a dark ground, the inset of a panel. Semantic tokens point at primitives, components point at semantic tokens, and nothing points at a hex code. Change the green in one place and every button, badge and link moves with it, on every platform, in one pull request. The file has a third reader now, a coding agent, and in Agent Review’s experiment both agent runs stayed on it: every value they wrote was a token, with the rules in front of them and without. The check runs the other way. A token lint reads every declaration against a typed list of the layer’s names, and on the branch I seeded with the failures the rules forbid it reported seventeen values written where a token existed, each with its file and line.

This is the part of the job I have done longest, on the Fiori program and in this site’s color spec, and it is the part where the tooling changes least. My color spec tabulates every ink on every ground with its measured ratio; Agent Review’s token layer does the same in a form a build and a lint can read. The discipline is identical. What the pipeline adds is that the discipline stops depending on anyone remembering it.

Key idea 4 of 8

A pull request is a design review with the evidence attached

A pull request is a proposed change to the codebase with its reasoning written above it and its difference rendered below it, and it is where a design engineer spends more of the day than any tool with a canvas. Reading a diff is how a designer sees what actually shipped rather than what was intended. Opening one is how a designer proposes a change that engineering can accept with a click instead of scheduling a meeting to describe.

The postings say “comfortable participating in pull request reviews,” and at nine in the morning that means: read the change, open the story, press the states, and leave a comment on the line rather than in a channel. Agent Review is my attempt at designing that review for a change an agent wrote. The change opens to its findings, with the affected screen rendered from the branch beside them, before and after, at three widths, and selecting a finding puts the preview in the state that shows it. The first run’s review turned on twelve lines in a shared Table stylesheet and the agent’s own measurement of the head row before and after, which is the kind of evidence a pull request exists to carry.

On a team the review also runs the other way. A component I wrote is read by an engineer who sees the failure modes I do not, and the review is not a gate the design has to pass; it is the second pair of eyes the design has been missing. On this site almost every change goes through a branch and a pull request too, and the pull request is where I read my own diff beside the checks.

A design engineer is a designer whose deliverable is the thing itself, in the repository, next to everyone else’s.

Key idea 5 of 8

The prototype is a branch, not a file

Here is the day, in order, for a change that begins as an idea rather than a ticket.

The tools that changed this are the ones that write code from a description: Claude Code in a terminal, which is what Agent Review was built with, and editors such as Cursor that do the same job. They took the mechanical barrier out of the middle of that list. A working prototype on a branch used to cost a week of an engineer’s time; the mechanical part of it is now a session, and the time goes to the decisions rather than the syntax. Agent Review’s experiment is that list run three times: one feature request, bulk actions on a customer table, on three branches. Two were written by a coding agent, one with the rules in its context and one without, and the third I wrote by hand. All three open in the review tool as changes with findings.

What those tools do not take out is the judgment. The posting that says a design engineer should use AI without relying on it has the emphasis right. The two agent runs read the same rule about shared components and did opposite things. One changed twelve lines of the shared Table stylesheet and showed its measurement; the other measured the same defect and flagged it instead. Both were defensible, and it took a person reading the measurement to say which was right. The prototype is real because I can read what it does, not because something wrote it quickly. The branch is where that reading happens, and the pull request is where it is shown.

Key idea 6 of 8

Motion is code you can review

The craft the postings name most precisely is motion: easing curves, spring physics, transitions that can be interrupted halfway and reversed without a stutter. In a design tool those are a demo somebody plays in a meeting. In the codebase they are a handful of values in the token file and a component that reads them: a duration, a curve, a spring’s stiffness and damping. Framer Motion, now simply called motion, does the physics for React; plain CSS transitions do most of the rest, and a motion spec of six durations and one curve covers a whole site.

Code does not make motion easier to write, but it does make it reviewable. A transition can be opened in Storybook, played, interrupted, played again at a reduced-motion setting, and commented on by line. A spring that overshoots by a hair is a number a colleague can change, and the change is a diff. That is what “design owns quality end to end” means in the one part of the interface where quality used to be unownable, because nobody could point at it.

Key idea 7 of 8

The checks are part of the design system

A design rule that is not a script is a wish. Contrast floors, type scales, token coverage, whether a toolbar fits its box at tablet width: every one of those can be measured on the rendered page, and a design engineer’s last responsibility is to make sure they are. Agent Review has three instruments for it. A token lint fails when a component writes a value where a token exists. Vitest runs every story in Chromium with axe set to fail on violations. Playwright holds the screens to their visual baselines and every toolbar to its own box at 768. Each caught a different part of the branch I seeded with drift.

The seeded branch also found a check that could not fail. The first version of the 768 test measured the frame’s scroll width, and the bar’s parent clips its overflow, so a bar 58 pixels too wide passed. Checks are code, and code has defects; a branch built to fail is how you find which of yours cannot. This site holds itself to the older, larger version of the same instinct: ten checks, and five of them render every page in a real browser. I wrote them because the rules were written down and nothing held the pages to them, and the first pass found failures no eye had caught, a caption on the hero among them, which the craft article tells. A design engineer is the person on the team who thinks a design rule is a test, and writes it as one.

Key idea 8 of 8

A green check and a live site are two different facts

Then comes the lesson the tools teach hardest. A green check means the tree passed. It does not mean the site changed. The merge and the deploy are two separate machines that fail independently, and I learned that from a merge that ran every check, went green, and never deployed at all. The site did not look broken. It looked unchanged, which is indistinguishable from a change nobody made. Another deploy failed fourteen seconds in, on a green tree, because it carried one file the deploy machine could not follow. And a page fetched straight after a successful deploy can still show the old bytes, because the host caches for ten minutes.

Agent Review had the same lesson in miniature. Its first visual pass found a dev server from a different checkout already on the port, measured that tree, and passed, including a comparison it could not have passed. The fix was for the tests to start their own server and never reuse one. A check can be green and still have measured the wrong thing, which is the same gap from the other side.

So the last step of every change is to go and look, with a cache-buster on the address, at the page a stranger would get, and when the page says nothing, to read the log, because the interface goes quiet exactly when the record gets interesting. Once you have been caught by the gap between “it passed” and “it is live,” you stop confusing the two.

So the honest map of the job, for me, has three regions. Tokens, systems, accessibility and the checks around them: that is the work I have done longest, in enterprise programs and on this site, and the part I would run on day one. React, TypeScript, Storybook, branches, pull requests and tests: that is the work I do now, on Agent Review and on this site, as the way I carry design decisions into code and check them there, and I would expect to be fluent in a team’s own conventions within a quarter. A production React codebase with a team shipping to customers on a release train: that I have not run, and one project with one author is not a substitute for it. I would rather write that sentence here than have someone else write it about me.

In one breath

A design engineer is a designer whose deliverable lives in the codebase. The component replaces the spec, the token file replaces the parity meeting, the pull request replaces the handoff, the branch replaces the demo, and the checks replace the hope that everyone remembered the rules. The judgment is the same, carried further into the implementation and the checks; it just has evidence attached now, and the last piece of evidence is the live page, not the green check.

If you do one thing: open your team’s repository, find one component you designed, and read its file. Everything you cannot follow is the next thing to learn, and everything you can is already yours.

If this is the situation you are in: how I carry the direction into something that works, in real code on real inputs. The accounts this draws on: Agent Review, where a component system, its rules and an agent’s work went through one review, and how I built this site, where the rules became checks.
