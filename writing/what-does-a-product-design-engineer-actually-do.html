What does a product design engineer actually do?

The same thing a product designer does, carried into the codebase. The component is the deliverable, and the judgment doesn’t move: it gets attached to evidence. The worked example is Agent Review, a React and Storybook system I built.

In this article

  1. The handoff did not move; it dissolved
  2. The component is the deliverable, and it lives in one place
  3. A pull request is a design review with the evidence attached
  4. The checks are part of the design system
  5. A green check and a live site are two different facts

Key idea 1 of 5

The handoff did not move; it dissolved

For years a design job was a document that went somewhere else. You made the file, somebody built from it, and quality leaked out in the gap between the two.

AI coding tools moved that line. I came to this from product design, enterprise design systems and UX architecture, not engineering, and I now use React, TypeScript and Storybook to carry that work into code.

A design engineer is a designer whose deliverable is the thing itself, in the repository, next to everyone else’s. The evidence here is one project built that way, Agent Review, and this site.

Key idea 2 of 5

The component is the deliverable, and it lives in one place

In a product codebase the unit of design is a component: a button, a data table, a status line. In TypeScript its properties are typed, so the contract between design and engineering is a list the compiler reads.

Agent Review has fourteen components and 284 stories in Storybook, and every story is also a test: Vitest renders it in Chromium and runs axe on it. A state with no story is a state nothing checks.

Under the components is one file of tokens. Semantic tokens point at primitives, components point at semantic tokens, and nothing points at a hex code, so changing the green moves every button in one pull request.

Motion lives there too: a duration, a curve, a spring’s stiffness. A transition in Storybook can be played, interrupted and commented on by line, so a spring that overshoots by a hair is a diff.

Code doesn’t make motion easier to write. It makes it reviewable.

Key idea 3 of 5

A pull request is a design review with the evidence attached

A pull request is a proposed change with its reasoning above it and its difference below it. A design engineer spends more of the day there than in any tool with a canvas.

At nine in the morning that means: read the change, open the story, press the states, and leave a comment on the line rather than in a channel.

A working prototype on a branch used to cost a week of an engineer’s time. With Claude Code in a terminal the mechanical part is a session, and the time goes to the decisions.

In Agent Review’s experiment, two agent runs read the same rule about shared components and did opposite things. One changed the shared data table’s stylesheet; the other flagged the same defect. Both were defensible.

It took a person reading the measurement to say which was right. The prototype is real because I can read what it does.

A design engineer is a designer whose deliverable is the thing itself, in the repository, next to everyone else’s.

Key idea 4 of 5

The checks are part of the design system

A design rule that isn’t a script is a wish. Contrast floors, type scales, token coverage and whether a toolbar fits its box at tablet width can all be measured on the rendered page.

Agent Review has three instruments, a token lint, axe in Vitest and Playwright’s visual baselines, and each caught a different part of a branch I seeded with drift:

The seeded branch also found a check that couldn’t fail: the first 768 test measured the frame’s scroll width, and the parent clipped the overflow. Checks are code, and code has defects.

This site runs eleven checks, and six of them render its pages in a real browser. I think a design engineer is the person who reads a design rule as a test, and writes it as one.

Key idea 5 of 5

A green check and a live site are two different facts

A green check means the tree passed. It doesn’t mean the site changed. I learned that from a merge that ran every check, went green, and never deployed.

The site didn’t look broken. It looked unchanged, which is indistinguishable from a change nobody made.

So the last step of every change is to look at the page a stranger would get, with a cache-buster on the address.

The honest map of the job, for me, has three regions:

  • Tokens, systems, accessibility and the checks around them: I’ve done this longest, and would run it on day one
  • React, TypeScript, Storybook, branches and tests: I do this now, and would expect to be fluent in a team’s conventions within a quarter
  • A production React codebase shipping to customers on a release train: I haven’t run one, and one project with one author is no substitute

I’d rather write that last line here than have someone else write it about me.

In one breath

A design engineer is a designer whose deliverable lives in the codebase: the same judgment, now with evidence attached, and the live page as the last piece of it.

If you do one thing: open your team’s repository, find one component you designed, and read its file. Everything you cannot follow is the next thing to learn, and everything you can is already yours.
