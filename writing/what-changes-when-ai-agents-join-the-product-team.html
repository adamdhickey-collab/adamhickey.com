What changes when AI agents join the product team?

The design system stops being a library people consult and becomes the instructions a builder follows. An agent can’t ask what you meant, so the meaning has to be written down.

In this article

  1. The newest builder on the team can’t ask what you meant
  2. A paved road works better than a fence
  3. Write down what things mean, not only how they look
  4. Drafting an interpretation isn’t the same as owning it
  5. One rule now repeats across a hundred screens, for better or worse

Key idea 1 of 5

The newest builder on the team can’t ask what you meant

Think about your first month on a product team. You read the design system, and then you learned the rest by asking. Why does that warning only appear when money moves? Why does this screen look odd? Somebody remembered.

Now add a coding agent to the team. It reads the docs in seconds, builds screens from the system and opens a pull request before lunch. It can’t do the one thing you did that first month: ask.

Whatever the system doesn’t write down, the agent decides. And every check still passes, because the checks only know what was written down too.

Key idea 2 of 5

A paved road works better than a fence

The obvious answer is a fence: lock the components down and refuse anything off the pattern. It stops mistakes. It also stops the new thing the product needed.

No fence is worse. Give an agent a workflow that none of your three data tables fits, and it will happily build a fourth.

Szymon Chudy, on Netflix’s design system team, calls the alternative a paved road (opens in a new tab): the system’s way is the easiest way, and its context ships with it.

More than two thousand apps depend on it, too many to fence one at a time.

The exit is where the judgment shows. In the experiment behind Agent Review, an agent could change a shared component only with a written reason: what it measured, where, before and after.

Make the right way the easy way, and mark the exits.

Key idea 3 of 5

Write down what things mean, not only how they look

Most design systems say how a confirmation dialog looks. An agent building one needs to know when it’s needed at all, and what to do when it can’t tell.

Agent Review’s simulated run has a small version of the same gap. Every action is the system’s Button except “Cancel subscription,” small gray text built by hand. The checks pass whichever way the agent goes.

Should cancel be that hard to find? I don’t think a check can answer that. A person can, and the answer belongs in the system. It’s written up in What a design system needs to explain to an agent.

The meaning is the part a builder who can’t ask will get wrong.

Whatever the system doesn’t write down, the agent decides.

Key idea 4 of 5

Drafting an interpretation isn’t the same as owning it

Agents don’t only build the screens now. They write what goes on them: the summary, the analysis, the recommendation a person acts on.

Imagine one looking into a metric that jumped overnight. It reads the logs, finds a likely cause and writes a confident summary. The summary might be right. It might also be a good story told from half the evidence.

Shown with the same weight as a signed-off report, a guess reads as a finding.

So the system needs a look, words and rules for “the AI wrote this, and nobody has checked it yet.” More in What does a design system need once AI is in the product?

A draft is a state, and the system has to be able to say so.

Key idea 5 of 5

One rule now repeats across a hundred screens, for better or worse

A component built wrong used to hurt the few screens it was placed on. A rule written wrong now spreads to every screen an agent builds from it.

Give Agent Review’s Button a quiet variant, just so one cancel link can stay as it was, and any later agent can make any action that quiet, everywhere at once.

A fix spreads the same way. On the SAP program I led, a UX and accessibility check in the release process reached all forty-plus apps, even teams that never opened the style guide.

While the program ran, UI defects in production fell by roughly half.

But a well-run system full of mediocre decisions produces mediocre work, at scale. On the SAP program the judgment came from sitting with people through their workday.

Agent Review’s hasn’t come yet. It plays simulated runs, and I haven’t tested it with anyone, so its rules are my best guess.

The questions I spend more time on now:

  • What can an agent decide alone, what needs review, and what is never handed over?
  • Where does each part say what it means, so an agent will find it?
  • Where does the system admit what it doesn’t know?
  • When would following a rule produce the wrong outcome?

A system can carry a team’s judgment to every screen. It can’t supply the judgment.

In one breath

An agent can’t ask what you meant, so the design system has to say it: what each part means, a paved road with marked exits, and a state for a draft nobody owns yet.

If you do one thing: pick one action in your product that can’t be undone. Write down, where an agent will read it, when that action needs a confirmation and what the confirmation has to say.
