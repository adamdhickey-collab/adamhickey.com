The Shift: The job is changing

Lesson 3 of 12 · 3 min read

How do you write design quality down so an agent can use it?

Put it in three places: a design system that says why, not only what; checks that run on every change; and a definition of done written before the build starts. Judgment used to spread through reviews and handoffs. With agents building, it has to live in the system.

Three terms first

Design system as context
The components, tokens, and written rules an agent reads before it builds.
Automated check
A script that measures a change against a rule, every time, and refuses it if the rule fails.
Definition of done
What has to be true before work ships, written down before the work begins.

If designers own “ready to ship,” quality can’t stay a feeling

Dmitry Sergushkin heard Meaghan Choi describe a design process collapsed into two loops: decide what to build, and decide when to ship. His answer is that the second loop needs a definition, and the definition needs a home.

His evidence is one team’s: every mistake his coding agent made in their components traced back to a gap in the docs, and each one became a rule.

Every rule on this site came from a failure I found first

This site is held to four written specs by twelve checks that measure the rendered page. An AI wrote most of the scripts, to rules I set, and nearly every rule has a story.

A rule I’d once have written down and hoped to remember is now a script that refuses. That’s what “encoded” means in practice.

A passing check only proves what it measures

Some quality can’t be a script. In Agent Review’s simulated run, every check passed a cancel link that was quiet on purpose, or by accident. No check could say which.

I answered it, since I knew its history. So I wrote the answer down where the next agent would read it: on the billing screens, an action that ends a subscription never gets a quiet variant.

This has a cost. The site is slower to change than a template, because a change that moves a number has to move the sentence that states it. I think that’s the right price.

Judgment used to scale through people. Now it has to scale through what the system can read.

Try it: write one rule down

Optional, about twenty minutes. Take something your last design review caught, and turn it into a rule an agent could read.

See one of my rules, whole
  1. RuleText over a photograph clears 4.5:1.
  2. WhyA caption shipped at 3.88:1 over a photo, and no check caught it.
  3. CheckA script reads the contrast pixel by pixel.
  4. Still a personWhether the caption belongs on the photo at all.

From how I built this site.

Your turn, and how to tell it’s done
  1. Pick something your last review caught.
  2. Write it as one sentence a stranger could apply.
  3. Add the failure that taught it.
  4. Say how it’s checked: by a script, or by whom.
  5. Name the case where a person should overrule it.

It’s done when:

  • A stranger could apply the rule without asking you.
  • The check can fail.
  • The exception names who decides.

Check yourself

1What did your last design review catch that no document would have?

That’s a rule waiting to be written. If it comes up twice, it belongs in the system or in a check.

2Is your definition of done written before the build, or argued about after?

An agent can only meet a bar it can read. A bar set after the fact is a review, not a definition.

The idea: Dmitry Sergushkin, on Meaghan Choi’s uxcon vienna talk. The example: How I built this site.
