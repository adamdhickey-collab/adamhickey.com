What does a developer need from an interface on a bad day?

What anyone needs when work has stopped: what broke, what it affects, what changed and what’s safe to do next. Developers mostly open their tools when something has failed, so those answers are the product.

In this article

  1. The screens a developer opens most are the ones that open when something broke
  2. An error message is an interface, and most are written by the thing that failed
  3. The first ten minutes decide whether the tool is believed
  4. The log is the interface of last resort, so design it as one
  5. The questions come in an order, and the screen can follow it

Key idea 1 of 5

The screens a developer opens most are the ones that open when something broke

Nobody opens the dashboard when the deploy works. You get a green line in a chat window and go back to the editor.

You open it when the deploy fails, the build is red, or the bill doubled. So the screens people reach stressed and short on time are the ones that matter most.

I think that makes failure a first-class state, not an edge case. This small site has taught me so three times.

Key idea 2 of 5

An error message is an interface, and most are written by the thing that failed

Most error messages are written by the thing that failed: an engineer handling the exception, not the person who’ll read it.

“Deploy failed” is what this site’s deploy said the day it failed fourteen seconds in, on a tree that had passed every check. A folder had been committed as a link to a path on one Mac.

The check I wrote afterward names the link, where it points and why the upload can’t follow it, and it catches the problem before the push.

That decision gets made in a design review of the strings, with the engineer who owns the code that throws them in the room.

Worse than a bad error is no error. The build behind one of this site’s stylesheets skips any class it has never seen, silently, and the type measures wrong at every width with nothing in the console.

A merge that passed every check and never deployed didn’t look broken. It looked unchanged, and there was nothing to search for.

So make nothing look like something. An empty list says why it’s empty, and a deploy that didn’t run is a row that says so.

The empty state is the product telling the truth about a moment when it has nothing to show, and the truth is almost always a reason.

Key idea 3 of 5

The first ten minutes decide whether the tool is believed

A developer arrives with a repository and a deadline: sign up, connect, first deploy. What happens when that first deploy fails decides what the tool will ever be believed about.

If the failure explains itself, every later green line is read as true. If it’s a status, they keep a terminal open beside the product for as long as they use it.

Trust in a tool is a record of whether the thing said what it was doing, and people start keeping it in the first ten minutes.

The empty state is the product telling the truth about a moment when it has nothing to show.

Key idea 4 of 5

The log is the interface of last resort, so design it as one

Most of what a developer’s tools say, they say in a log. It’s the least designed surface in software, and it’s read at the worst moment.

So design it as an interface: the failing line first, the noise folded, the step names and times in a column the eye can run down.

The screen above it should be built from the same record, not a summary that can drift. And the record can be wrong too.

Two of this site’s browser checks once measured the wrong tree and printed the results under the right name. Now every one prints the path, page count and commit before anything else.

A summary is an interpretation of the record, so the screen has to let a person reach the evidence under it.

Key idea 5 of 5

The questions come in an order, and the screen can follow it

Ship through a developer’s tools for a season and a pattern shows. Whatever went wrong, my questions came in the same order:

  • What is live right now? The deploy log.
  • What failed? The check.
  • What changed since it last worked? The diff.
  • What depends on what changed? The history.
  • Can I put it back safely? The branch, because a change on one commit reverts with one.

A screen can be arranged in that order, top to bottom, and it can be dense, because a developer under pressure has plenty of data and little attention.

The first question is the one most screens answer badly. A list sorted newest-first puts a failed deploy on top, and a developer reads it as the one serving traffic.

So keep the word live for the deploy that’s serving, and make a failed build’s first sentence say nothing is down.

The order is mine, from shipping one site alone, so treat it as an assumption. On a team the first question may be who pushed.

What I run daily is the branch, the commit, the pull request, the checks and a static deploy. Containers and observability across many services I’ve read about and not run.

It’s close to the order an operations floor asks in, too, which is another article. Knowing the questions in order, from having asked them yourself, is the best qualification I know for designing the answer.

In one breath

A developer opens the interface when something broke, so the error, the empty state, the log and the first ten minutes are the product.

If you do one thing: find the last error your product showed a developer and rewrite it. Say what happened, to what, why, and the one thing to do. Then find the engineer who owns the code that throws it.
