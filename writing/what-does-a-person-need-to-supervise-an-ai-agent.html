What does a person need to supervise an AI agent?

More than an approve button. An agent takes a run of steps, so the person supervising it has to judge the whole run. The scenario below is an illustration, and the prototype it draws on recommends rather than acts.

Key idea 1 of 5

A recommendation is one decision; an agent is a run of them

Most of what I’ve written about AI here is about one decision: a system recommends and a person judges. Dispatch Cockpit, my prototype on synthetic data, is that shape exactly: one load, one truck, one press.

An agent is given a goal instead of a question, and takes a run of steps: read the failed order, find the missing field, look up the partner’s rule, draft the fix, resubmit.

Nobody is watching each step. That’s the point of it, and the problem. The unit a person has to judge is now the whole run.

Picture an agent working the overnight queue of failed orders. By morning it has touched forty. The specialist who arrives at seven needs to know:

  • Which of the forty it was sure about
  • Which it wasn’t
  • What it did when it wasn’t
  • Whether any of that can still be undone

Key idea 2 of 5

Draw the line where a mistake gets expensive, not where it gets possible

The first design decision is made off the screen: the line between what the agent may do alone and what it has to ask about. I’d draw it where a mistake gets expensive to reverse.

Reading an order costs nothing to get wrong. Resubmitting it costs a phone call. Changing the rule for every order from that partner costs a week.

The person supervising the agent has to see where the line is, and move it for one partner or one kind of order, without opening a ticket.

Autonomy is a boundary in the workflow, and engineering has to enforce it where the copy describes it.

Key idea 3 of 5

Approval is a question with the evidence attached

When the agent reaches the line, it asks, and how it asks is most of the interface. “Resubmit order 4471?” teaches people to answer yes, because there’s nothing in it to judge.

The question that works carries its evidence:

  • This order failed on a missing customer identifier
  • Eleven others from this partner are missing the same field since Tuesday
  • The corrected document beside the original, with the change marked
  • The last time this correction was made, and what happened

Two more things belong on it and are usually missing: what happens if nobody answers at three in the morning, and whether a yes covers this order or teaches the agent to stop asking.

An approval without the evidence is a rubber stamp, and the rubber stamp is what the agent was supposed to replace.

Design psychology

When in doubt, do less, and say so

The one human–AI guideline I’d keep is to scope the service when in doubt: ask or do less, rather than guess and do more. A step held for a person is cheaper than a confident wrong one.

Key idea 4 of 5

The run has to be readable afterward, by someone who was not there

Whatever the agent did alone has to be readable afterward by someone who wasn’t in the room, which is a stronger word than logged.

The specialist at seven needs the forty grouped: the three that hit the line and waited at the top, the one it skipped next, and the thirty-six it resubmitted folded away until something looks wrong.

Dispatch Cockpit writes only half of this, and its page says so. It saves the override reason, and not what it recommended on which figures.

Stopping is where the record matters most. Stopping before the next step is easy, and undoing the last one depends on the record. Handing a half-done queue back to a person is the stop nobody designs.

The failure halfway through is the ordinary case, so the interface for it is the interface for the whole thing.

If a decision can’t be reconstructed from the record, the agent wasn’t supervised. It was trusted.

Key idea 5 of 5

The instruction is a design surface, and the test is the other half of it

The agent does what its instructions say, and they’re written by someone who isn’t an engineer: the specialist, the dispatch manager. That makes the instruction a design surface, and most are a text box.

An instruction needs what a good form needs: what it changes, which cases it covers, and what it conflicts with. Then a way to replay last night’s forty under it, with every changed decision marked.

I tried a small version in Agent Review, where a coding agent reads twelve written rules, each naming the command that checks it. Run with the rules and without, one feature request stayed inside the component system both times.

One request and two runs is a small sample. It suggests the instruction is a smaller lever than it looks, and the test is where the control actually is.

So the measure that matters is what the person caught: what got stopped before it cost anything, what got through, and whether the next night went better than the last.

An agent that finishes everything and is never caught is either perfect or unsupervised, and the dashboard can’t tell you which.

In one breath

An agent is a run of decisions, so the person supervising it needs a line, evidence on every question, a readable record, a way to stop and a test for every instruction.

If you do one thing: before you design the agent’s good night, design the morning after it failed at step twenty-two. Show that screen to the person who would open it.
